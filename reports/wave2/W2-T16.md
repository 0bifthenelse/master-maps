## 2. Slim manifest (`app/api/map/manifest/route.ts`)

### 2.1 What the route now serves

The wire body keeps every field the client needs and drops the four duplicated top level maps
plus the per tile string arrays:

Kept: `datasetVersion`, `acquisitionTime`, `territoryCode`, `territoryName`, `interchangeCrs`,
`processingCrs`, `renderOrigin`, `boundary`, `projectionOrigin`, `bounds`, `tileSize`,
`tileCount`, `tiles`, `lods`, `featureCounts`, `layerAvailability`, `pipeline`, `sources`,
`failedSources`, `transformation`, `version`, `nocibeFocus` (when present).

Dropped: `tileIds`, `tileBounds`, `byteSizes`, `tileFeatureCounts` (all four are exact duplicates
of data still present inside `tiles[]`).

Slimmed per tile entry: `tileId`, `lod`, `bounds`, `byteSize`, `featureCount`.
Dropped per tile entry: `features`, `fragmentIds`, `fragmentOf`, `geometryBounds`.

The response is still produced through `DatasetManifestSchema.parse`
(`app/api/map/manifest/route.ts:35`), so any future consumer that validates the body keeps
working. VERIFIED by `tests/unit/manifest-slim.test.ts:163`.

### 2.2 Measured byte size for the current dataset

Computed from the real `data/generated/manifest.json` and the real
`data/generated/tile-manifest.json` (9 591 tiles), reproducing the route logic exactly
(`JSON.stringify` compact separators, same key set):

```
slim manifest bytes (JSON.stringify compact): 1053529
fat manifest bytes:                            133617306
ratio:                                         126.8
slim gzip bytes (level 6):                     171414
slim tiles array alone:                        1050260
tile-manifest.json on disk:                    152616541
```

So 99.2 percent of the response was the `features[]` / `fragmentIds[]` arrays, which is exactly
what `reports/wave1/W1_T06_NETWORK.md:15` predicted (it estimated 1.05 MB, we measure
1 053 529 B). The `tiles[]` array now accounts for 1 050 260 of the 1 053 529 bytes, i.e. the
manifest envelope itself is down to 3 269 bytes.

### 2.3 Cache path

`MappedFileCache` (`src/lib/data/mappedCache.ts`) is the shared primitive: a `Map` keyed by path,
each entry holding `(versionKey, value)`, where `versionKey` is `${mtimeMs}-${size}`
(`src/lib/data/mappedCache.ts:13`). `get()` stats the file, compares the version key, and either
returns the cached value or loads once. Concurrent `get()` calls for the same path share a single
in flight promise (`src/lib/data/mappedCache.ts:44`), so a cold burst of parallel requests
still reads the 152 MB file exactly once. Eviction is LRU bounded by `maxEntries`.

For the manifest the version is the max mtime and the summed size of `manifest.json` and
`tile-manifest.json` (`app/api/map/manifest/route.ts:21-27`), so regenerating either file
invalidates the cache.

Cache headers (`app/api/map/manifest/route.ts:70-76`):

- `Cache-Control: public, max-age=60` (was `public, max-age=3600, must-revalidate`)
- `ETag: <datasetVersion>`
- `X-Dataset-Version: <datasetVersion>` (unchanged behaviour)
- `Vary: Accept-Encoding`

A matching `If-None-Match` returns 304 with an empty body
(`app/api/map/manifest/route.ts:77`). Error responses are `503 DATASET_UNAVAILABLE` on ENOENT
and `500 DATASET_INVALID` otherwise, identical to the previous semantics, now with
`Cache-Control: no-store` so a failed build is never cached.

### 2.4 Schema dependency (resolved by Main)

`TileManifestSchema.features` was required in the committed schema
(`src/lib/data/schema.ts:341` before the Wave 2 change), so dropping it from the wire body made
`DatasetManifestSchema.parse` fail with `expected array, path: ["tiles", 0, "features"]`. Main
relaxed it to `.optional()`. The route now emits tile entries with no `features` key at all.
`fragmentIds`, `fragmentOf` and `geometryBounds` stay optional as before.

## 3. New render route (`app/api/map/render/[tileId]/route.ts`)

`export const dynamic = "force-dynamic"` (`app/api/map/render/[tileId]/route.ts:7`).
This is deliberate: a `force-static` route is built once and replayed from the Next data cache,
so a rebuilt dataset would be invisible. The `immutable` decision is made per request from the
`?v=` query parameter instead, which is the mechanism the contract specifies.

### 3.1 Tile id validation

`isValidRenderTileId` (`app/api/map/render/[tileId]/route.ts:17`) applies the same
`TILE_ID_RE = /^[a-zA-Z0-9_-]+$/` rule as the other routes and additionally rejects:

- empty or over 128 characters
- `..`, `/` and `\` (path traversal and separators)
- ids ending in `.json`, `.mmt` or `.gz`, which closes the extension suffix confusion noted in
  `reports/wave1/W1_T06_NETWORK.md:21` (F7). A request for `tile.json` is a 400, not a 400 by
  accident of the regex: the rule is explicit.

A rejected id yields `400 INVALID_TILE_ID`.

### 3.2 Payload selection and streaming

The route stats `<tileId>.mmt.gz` first (`app/api/map/render/[tileId]/route.ts:95`). If it
exists it is served with `Content-Encoding: gzip` and the correct `Content-Length` from the
sidecar stat. Otherwise it falls back to `<tileId>.mmt` with no `Content-Encoding`
(`app/api/map/render/[tileId]/route.ts:102-104`). The body is a `createReadStream` converted
through `Readable.toWeb`, so a 20 MB render tile is never buffered in route memory.

`Vary: Accept-Encoding` is set on every 200 (`app/api/map/render/[tileId]/route.ts:89`), which
is mandatory once the same URL can return two different encodings.

### 3.3 Cache control

`isPinnedToDatasetVersion` (`app/api/map/render/[tileId]/route.ts:24`) is true only when
`?v=` is present, non empty, and equal to the current `datasetVersion`. Then
`Cache-Control: public, max-age=31536000, immutable`
(`app/api/map/render/[tileId]/route.ts:13`). In every other case, including a stale `?v=`,
the response is `no-store` (`app/api/map/render/[tileId]/route.ts:14`).

`X-Dataset-Version` is always present on 200 responses
(`app/api/map/render/[tileId]/route.ts:87`).

### 3.4 Dataset version cache

The route reads `datasetVersion` once and memoises it at module level, with a single in flight
promise (`app/api/map/render/[tileId]/route.ts:40-60`). The manifest is never re-read per
request. VERIFIED by `tests/unit/render-route.test.ts:151`.

### 3.5 Status codes


- `400 INVALID_TILE_ID` for a bad id
- `503 DATASET_UNAVAILABLE` when the dataset manifest is missing, or when neither `.mmt` nor
  `.mmt.gz` exists
- `500 DATASET_INVALID` when `manifest.json` is unparseable or a stat fails with a non ENOENT
  error

The error body shape `{ error, code }` is copied from the tile route, and error responses always
carry `Cache-Control: no-store`.

## 4. Tile route (`app/api/map/tile/[tileId]/route.ts`)

The response envelope is unchanged: `TileDataSchema.parse({ manifest, features })`. What changed:

- **LRU cache of 64 entries** (`app/api/map/tile/[tileId]/route.ts:18`), keyed by the tile file
  path and invalidated by `${mtimeMs}-${size}` of that tile file. A cache hit does no read and no
  Zod parse at all, which removes the 152 MB manifest scan and the per feature parse from the
  hot path identified in `reports/wave1/W1_T06_NETWORK.md:244`.
- **ETag equals `datasetVersion`** (`app/api/map/tile/[tileId]/route.ts:98`), with a 304 path at
  `app/api/map/tile/[tileId]/route.ts:102`. This was finding F9 in
  `reports/wave1/W1_T06_NETWORK.md:23`.
- `X-Dataset-Version` header added (`app/api/map/tile/[tileId]/route.ts:99`).
- `datasetVersion` is read once and memoised
  (`app/api/map/tile/[tileId]/route.ts:45-60`), so the ETag costs no per request read.
- Status semantics preserved: 400 invalid id, 413 too large, 503 missing file or missing from
  the manifest, 500 schema failure. The "present on disk but absent from the manifest" case now
  carries an explicit `TILE_NOT_INDEXED` code instead of relying on an error message substring
  (`app/api/map/tile/[tileId]/route.ts:29`).

`Cache-Control` for tiles is deliberately left at `public, max-age=3600, must-revalidate`:
these are inspector detail fetches, not the render path, and the legacy JSON tiles are still
regenerated in place by the pipeline, so a version independent immutable window would be wrong.

## 5. Search index (`scripts/data/build-search-index.ts`)

### 5.1 Before

`boostFor` returned a value only for business (200), poi (100), address (50) and building (10).
Place and transport records fell through to 0, `categoryFor` returned `undefined` for them, and
`featureName` relied on `feature.name` or `feature.displayName`. Streets were already covered:
`aliases` and `categoryFor` both have an explicit `kind === "road"` branch.

### 5.2 After

`scripts/data/build-search-index.ts:137-148` adds two lookup tables:

```
PLACE_IMPORTANCE_BOOST   = { 0: 20, 1: 40, 2: 60, 3: 80, 4: 100, 5: 120, 6: 140 }
TRANSPORT_BOOST          = { station: 40, halt: 30, bus_stop: 25, platform: 25,
                             aerodrome: 35, runway: 20, parking: 20 }
TRANSPORT_BOOST_DEFAULT  = 15
```

`boostFor` maps `place.importance` (1 to 6 per `CONTRACTS.md` section 1) through
`PLACE_IMPORTANCE_BOOST`, with importance 0 as the unknown case at 20, and maps
`transport.transportType` through `TRANSPORT_BOOST` with a 15 default. A more important
settlement therefore outranks a lesser one, and a station outranks a bus stop, which is the
ranking the contract asks for. A place record still below poi (100) and business (200) is
intentional: a municipality should not outrank a shop that carries the same name.

`categoryFor` now returns `placeType` for place and the most specific of
`publicTransport`, `line`, `route`, `transportType` for transport, and the street name for
address (`scripts/data/build-search-index.ts:150-159`).

`featureName` composes `"<housenumber> <street> <postcode> <city>"` when an address has no
`name` field (`scripts/data/build-search-index.ts:117-124`), and `aliases` gains the address
street and city plus the transport name (`scripts/data/build-search-index.ts:105-115`). The address
branch matters because BAN address features carry their components in structured fields, not in
`name`; without it a large share of the 115 379 address records was reachable only through the
coarse `feature.address` string.

### 5.3 Completeness on the current dataset

Measured over `data/intermediate`, records by kind that have both a resolvable name and lon/lat:

```
address  115379
road      85900   (named roads)
poi       34618
business     611
place          0
transport      0
```

The current index holds 254 830 records (`address` 115 379, `road` 85 900, `poi` 34 618,
`water` 18 322, `business` 611). The named address, road, poi and business sets are therefore
already fully covered at 236 508 records. Place and transport are 0 in `data/intermediate`
today because the BD TOPO `zone_d_habitation` and OSM transport layers have not been built into
the dataset yet; the code path is in place and exercised by
`tests/unit/search-kinds.test.ts`, which feeds synthetic place and transport features through the
real `buildSearchIndex`.

### 5.4 `searchServer.ts` (no change required)

`src/lib/data/searchServer.ts` needed no edit. `SearchRecordSchema.kind` is
`z.enum(FEATURE_KINDS)` and `FEATURE_KINDS` already contains `place` and `transport`
(`src/lib/data/schema.ts:332`), the loader validates every record through that schema, and the
3 character prefix bucket, the candidate selection, the direct scoring, the fuzzy tier and the 64
entry hit LRU are all kind agnostic. Place and transport records are therefore searchable the
moment the index contains them. Measured: the three existing search test files still pass
(28 tests).

### 5.5 Tile index file (pipeline coordination)

`loadData` built the `stableId -> tileId` map by iterating `manifest.features`
(`scripts/data/build-search-index.ts:94-101`). Once the pipeline writes the slim
`tile-manifest.json` that array is gone, so the lookup now goes through
`resolveTileIndexPath` (`scripts/data/build-search-index.ts:58-72`), which prefers
`data/generated/tile-index.json` and falls back to `tile-manifest.json`, and the iteration
tolerates a missing `features` array. This is the QA only file that keeps the string arrays
(`CONTRACTS.md` section 6). Confirmed by wave2-4, who own `build-tiles.ts`: the QA only
identity index is `data/generated/tile-index.json`, a sibling of `tile-manifest.json` reached
as `path.join(tilesDir, "..", "tile-index.json")`, holding full `TileManifestSchema` entries with
`features` and `fragmentIds` populated, one entry per final post-subdivision tile, in the same
order as `tile-manifest.json`, while `tile-manifest.json` itself keeps only
`{ tileId, lod, bounds, byteSize, featureCount }`. That is exactly the contract the resolver and
the loader above implement.
