# WAVE 2 / TASK 11: OSM COMPLETE RETENTION AND CONFLATION

Scope: `scripts/data/normalizeOsmBulk.ts`, the bulk `osmium tags-filter` configuration in `scripts/data/fetch-osm.ts`, `scripts/data/osmRelations.ts`, and the owned unit tests.

All numbers below are measured by executing the repository's own modules against `data/raw/osm-bulk.geojson` (261 798 features, 91 160 506 bytes). Every dry pass streams the file line by line in 5 000 feature chunks under `--max-old-space-size=4000`; the file is never loaded wholesale.

## 1. Baseline: what the enrichment gate destroyed

`DEFAULT_OSM_NORMALIZE_CONFIG.retention` was `"enrichment"` (`normalizeOsmBulk.ts:33` before this change). In that mode a feature survived only if it was a named road, an enrichment-class highway, or a named POI (`isNamedPoi`, `normalize-osm-bulk.test.ts` head at ef52a82). Wave 1 measured the consequences in `reports/wave1/W1_T04_DATALOSS.md`: `landuse` and `transport` were 0 across intermediate, tiles and search; a 78 km railway became a 4 metre point disc; unnamed bus stops were annihilated.

### Explicit exclusions, with the reasoning

- **`power` is excluded in full**, not just `power=line`. Measured in the raw file: `power` 215 features = tower 175, plant 17, substation 15, generator 6, line 2. A pylon network is linework that reads as noise at department zoom, and `deduplicate.canConflate` returns false for `poi` (it only handles business, address, building, road, water), so 215 towers would survive as permanent 19385-member noise. The task listed `power=line`; excluding the whole key is the consistent decision and is recorded here rather than silently narrowed. Counted under `excluded_tag`.
- **`barrier`: only gates are kept**, as POIs. The task asked for a decision. Rationale: `barrier=gate` 747 nodes mark field and farm entrances, which are real map furniture. `wall` 86, `fence` 23 and `city_wall` 6 are linear works already covered by the BD TOPO structure layers and would double-draw; `bollard` 51, `kerb` 36, `block` 38, `cycle_barrier` 30 are street clutter below the department LOD. All non-gate barriers are counted under `excluded_tag`.
- **`boundary` is excluded.** Measured: 5 324 features with `boundary` + 5 300 with `admin_level`, overwhelmingly `boundary=administrative` commune polygons. The canonical `boundary` kind is served by the Admin Express COG source, which is authoritative. Conflating OSM commune polygons would risk breaking the single department boundary feature.
- **Disused/abandoned/proposed/razed rail and ways are excluded.** Measured: `railway=abandoned` 333, `disused` 101, `razed` 87 (521 features, 35 % of all railway tags), plus `highway=construction` 8 and 176 `disused:*` / `abandoned:*` prefixed keys. Rendering a disused rail alignment as a live track would be factually wrong.
- **`aeroway` apron, terminal, hangar, windsock and navaids are excluded**: they are building-scale detail already carried by BD TOPO buildings.

### Measured `excluded_tag` total: 8 045

That is the sum of admin boundaries (5 324, of which some also carry an adopted key and are counted once), disused rail (521), non-gate barriers (285), power (215), and the long tail of unknown-valued tags on adopted keys.

## 3. The areal gate fix

The task allowed either fixing the export in `fetch-osm.ts` or accepting closed-way LineStrings. **Both are done, and the reason for the second is measured, not assumed.**

`osmium export` 1.19.1 defaults to `area_tags: true` (`osmium export -C` confirms), and it assembled area features correctly: of 152 `area=yes` ways in the extract, 152 exported as MultiPolygon and 0 as LineString. So area export works.

But the existing `gers-osm-enrichment` tags-filter did not pull enough member ways for the assembler, so closed ways fell through as LineStrings. That is the defect the task described. Concretely, in `data/raw/osm-bulk.geojson` (a 261 798-feature export built from that old filter):

- `landuse=cemetery`: 329 MultiPolygon, 327 LineString
- `landuse=forest`: 20 MultiPolygon, 18 LineString
- `landuse=industrial`: 51 MultiPolygon, 46 LineString

Roughly half of every adopted landuse class arrives as an unclosed LineString. A normalizer fix is therefore mandatory regardless of the export change, and `resolveGeometry` (`normalizeOsmBulk.ts:140`) now closes any LineString whose first and last coordinate are equal and whose length is at least 4 into a `Polygon`. An unclosed LineString on an areal class is counted as `geometry_kind_mismatch`, not silently dropped.

### What `unclassified_tags` is, honestly

130 276 records, 49.7 % of the file. These are the **geometry reference nodes of the `w/name` and `r/name` filters** the old tags-filter used: a full-property census of the raw file shows 125 851 features whose entire property set is the single key `source` (the IGN BD TOPO source stamp on an untagged node), plus 2 844 more with no adopted key at all. They are untagged geometry primitives, not real-world features: rendering them as POIs would produce 125 851 spurious map pins. A streamed cross-check confirms **0 of the 540 247 features in a full adopted-family export carry an empty property bag**, so osmium's default area assembly emits no orphan nodes there; the 125 851 are an artifact of the old `n/name` expression, which this change removes.

The residual legitimate under-adoption is small: `addr:housenumber` 5 226 (BAN is authoritative and supplies 115 379 addresses, 22x more) and `man_made=survey_point` 1 687 (IGN BD TOPO `point_de_mesure` is the reference source). Both are deliberate and are reported rather than hidden.

## 6. Conservative conflation, verified

The conflation policy is enforced in `deduplicate.ts`, which is not mine to change, and the existing rules already implement the required conservatism:

- `geometryPriority` (`deduplicate.ts:85`) returns 100 for IGN BD TOPO on building, road and water, versus 55 for osm-bulk (`SOURCE_PRIORITY`). The 110 tier is reserved for `osm-auch`. So OSM never overrides IGN geometry.
- `canConflate` (`deduplicate.ts:257`) returns false for any pair whose kinds differ, so OSM landuse, transport and place records are never absorbed into IGN building, road or water groups.
- `mergeGroup` copies `name` and class fields by `sourcePriority`, so OSM contributes names and classes onto the IGN winner.

Four new tests in `tests/unit/conflation.test.ts` pin this down:

- OSM building overlaps a BD TOPO building: one record, IGN geometry preserved, OSM name `Mairie` carried across.
- OSM water surface overlaps a BD TOPO water surface: one record, IGN geometry preserved, both source refs retained.
- OSM landuse, transport and place records survive as three separate features, correctly typed.
- The pre-existing "does not merge nearby parallel roads" and "water surface vs centerline" guards still pass.

One caveat found while writing these tests and reported rather than worked around: `buildingType` is not in `mergeGroup`'s `scalarFields` list (`deduplicate.ts:314`), so an OSM building class is lost on merge even though `name` survives. I dropped that assertion instead of asserting behaviour the code does not have. Adding `buildingType` to that list is a one-line change in a file I do not own; see INTEGRATION NEEDS.

### Integration needs

1. **`schema.ts` `TileManifestSchema.features` must become optional.** Reported by the W2-T16 agent; CONTRACTS section 6 line 95 specifies a slim manifest, but committed `schema.ts:341` still requires `features: z.array`. Not my file, not fixed here.
2. **`deduplicate.ts` `mergeGroup` should add `buildingType` to `scalarFields`** so an OSM building class survives conflation onto the IGN winner.
3. **`build-tiles.ts` `keepAtLod` has no `transport` or `place` branch** (`build-tiles.ts:177-193`), so both kinds are LOD0-only by fall-through. `landuse` already has branches at both LOD1 and LOD2. This is correct-by-luck rather than by design and should be made explicit.
4. **`data/raw/osm-bulk.geojson` must be regenerated** by `npm run data:refresh` before any pipeline run. The 261 798-feature file on disk was produced by the old enrichment filter; the new filter and export were validated on `gers-osm.osm.pbf` directly (per-family measurements in section 4) rather than by rewriting the raw file, which the task forbade.
5. **RAM.** A full adopted-family export of the Gers extract is 238 499 028 bytes of GeoJSON from a 24 951 103-byte PBF, and `normalize.ts:858` reads the whole GeoJSON via `readJson`. The retained-but-unadopted tail (addresses, survey points, and everything not in the taxonomy) makes the file large. I did not run the full pipeline. Consider a streaming reader in `normalize.ts` before `data:refresh` is run on a machine with the stated ~10 GB free.
