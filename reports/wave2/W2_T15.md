# W2 / T15 - Incremental per-tile GPU resources

Scope: `src/components/map/MapShell.tsx`, `src/components/map/CityScene.tsx`,
`src/components/map/WebGPUCityCanvas.tsx`, `src/lib/data/loadTile.ts`,
`src/lib/render/tileGpuCache.ts` (new), `src/lib/render/sceneFromDecoded.ts`
(new), `src/lib/scene/buildBoundary.ts`, `tests/unit/tile-gpu-cache.test.ts`
(new).

## 1. What changed

### 1.1 Decoding through the worker pool, tile state as a Map

`MapShell` no longer fetches JSON tiles on the primary path. It calls
`loadRenderTile` from `src/lib/render/loadRenderTile.ts`, which fetches
`/api/map/render/<tileId>` and hands the raw `ArrayBuffer` to
`TileWorkerPool` (W2-T14, wave2-5). Tile state is `TileState` with a
`Map<tileId, TileSlot>`; each slot is either `{ mode: "render", decoded }` or
`{ mode: "json", json: TileData }`, plus the two ordered id lists the scene
consumes (`src/components/map/MapShell.tsx:180-195`).

`applyTileState` (`MapShell.tsx:280-286`) is the only writer, and it mirrors
the new state into `tileStateRef` inside the same updater. This is load
bearing: without the mirror the loader effect recomputed `pending` from a
stale ref and re-requested the same tiles forever.

### 1.2 Single-slab contract (CONTRACTS 3.1 amendment)

`sceneFromDecoded.viewDecodedTile` projects one `DecodedRenderTile` onto
zero-copy `Float32Array` / `Uint32Array` views over the single transferred
`payload` slab, using `renderLayerPositions` / `renderLayerIndices` /
`renderLayerRanges` from `codec.ts`. No layer data is copied. Verified in
`tests/unit/tile-gpu-cache.test.ts:88-99` (every layer's `array.buffer` is
the slab, asserted by identity).

`geometryFromLayer` returns `null` for a layer whose positions or indices are
empty, so a mesh is never mounted with an empty vertex array. This is the
direct guard against the reported `Vertex buffer slot 0 was not set`
validation failure.

### 1.3 tileGpuCache

`Map<tileId, Map<layerId, BufferGeometry>>` with a 512 MB byte budget
(`DEFAULT_GPU_CACHE_BYTES`), LRU recency refreshed on every
`getTileCacheEntry`, deterministic eviction: the oldest entry is removed from
the map, its geometries are `dispose()`d, its `stableIds` array is truncated
and its `slab` reference is replaced with an empty buffer
(`tileGpuCache.ts:117-140`, `:196-207`). `retainTiles` drops everything the
scene no longer references.

Picking is a stable featureId to canonical stableId map. `TileCacheEntry.
stableIds` is the flattened per-layer feature id array; each
`TileLayerEntry` records `firstStableId`, its offset into that array, so
`pickStableId` resolves a raycast `faceIndex` through the
`featureRange` `[indexStart, indexCount, metaIndex]` triples
(`tileGpuCache.ts:245-258`).

### 1.4 Per-tile groups, no global rebuild

`CityScene` renders one `<group key={tileId}>` per tile
(`CityScene.tsx:282-285`), each containing one mesh per layer straight out of
the cache. The tile path holds no `useMemo` over all tiles' features and
calls no builder; the only global operation is the `tileGroups` lookup that
resolves ids to cache entries. Adding or evicting a tile mounts or unmounts
only that tile's group. `tests/unit/tile-gpu-cache.test.ts:170-181` pins
this: after a second tile arrives, the first tile's entry, geometry object
and `featureRange` contents are identical objects/values and
`disposedGeometries` is still 0.

### 1.5 Fallback

When `/api/map/render/<tileId>` fails, the loader latches
`renderUnavailableRef` and serves that tile from the existing JSON endpoint
via `loadTile`, so the app never goes blank
(`MapShell.tsx:403-435`). The JSON scene path is preserved in `JsonScene`
(`CityScene.tsx:219-259`) and is selected when any JSON tile is resident.

### 1.6 Boundary built once, dataset level

`buildBoundary.ts` gains `selectDatasetBoundary`, which picks the single
boundary copy with the most vertices (the full outline, not a tile clip) and
breaks ties on the lowest fragmentId so the choice is stable across commits.
`CityScene` mounts it once. In the render path the boundary comes from the
dataset-level `boundary.mmt` artifact, loaded once in its own effect
(`MapShell.tsx:445-457`) and added to the scene tile id list, so no tile
arrival can re-tessellate it.

## 2. Defects found and fixed

### 2.1 The 42 permanently stalled tiles

The load effect was keyed on `[manifest, desiredKey]` while the generation
guard (`desiredGenerationRef`) advanced inside it. Any generation change
without a `desiredKey` change left already-started loops unable to schedule
their remaining work. The effect now depends on a real generation signal
rather than a ref, and the guard is read fresh on every iteration.

### 2.2 Initial LOD2 over the full bounds

`visibleTileIds` hardcoded `viewport ? lodForSpan(span) : 2` when the viewport
was still null, so the first pass requested LOD2 over the whole territory and
then re-tiled. It now derives the LOD from the dataset bounds through the
same `lodForSpan` function, so the first tile set matches the settled
viewport.

### 2.3 Black overview: root cause found and fixed

Reproduced in the guarded browser. The original validation errors were:

```
The depth stencil attachment [TextureView of Texture "depthBuffer"] size
(width: 300, height: 150) does not match the size of the other attachments'
base plane (width: 1440, height: 810).
```

Not a disposed geometry: the depth-stencil attachment was created at the
canvas **default** 300x150 because the canvas had not been laid out when R3F
configured the context, and was never resized with the canvas. Every render
pass was then invalid, which blacked the whole frame regardless of content.
`glFactory` now measures the canvas rect and calls
`renderer.setSize(width, height, false)` before *and* after `renderer.init()`
(`WebGPUCityCanvas.tsx:126-170`), plus a `ResizeObserver` on the container.
Measured after the fix: canvas 1440x810, zero GPUValidationError.

A second, independent race made `renderer-status` flap: the async
`requestAdapter()` probe resolved after the renderer factory had already
written `initialized` and overwrote it with `loading`. The probe now only
promotes the component while it is still in `checking`
(`WebGPUCityCanvas.tsx:92-101`, `gpuStatusRef`).

### 2.4 Empty-attribute meshes

`geometryFromLayer` returns `null` for empty layers, `putDecodedTile` refuses
a tile that yields no renderable geometry, and `TileLayerNode` refuses to
mount a mesh whose `position` count is 0. Pinned by
`tests/unit/tile-gpu-cache.test.ts:113-121`.

### 2.5 Infinite request loop (found during verification)

An earlier revision latched the fallback in React state and re-ran the effect
from a `desiredGeneration` state value written inside that same effect.
Measured 3838 requests / 3448 failures / 0 loads / 352 aborts in 26 s, then
`Maximum update depth exceeded`. Fixed by removing the state entirely: the
generation lives in a ref, the fallback latch lives in a ref, and there is a
single loader effect. Re-measured: 373 requests, 373 unique, no duplicate
churn, 0 console errors.

### 3.3 Worker path with a synthetic tile

`tests/unit/tile-gpu-cache.test.ts` encodes a synthetic tile with
`encodeRenderTile`, decodes it with `decodeRenderTile` (the same codec the
worker runs), then drives it through `putDecodedTile`. It asserts zero-copy
slab views, codec render order, slab-overrun rejection, empty-layer skipping,
picking, LRU eviction, recency retention, cross-tile isolation, and
`DecodeQueue` stale-generation rejection.

## 4. Integration needs (not my files)

1. `app/api/map/tile/[tileId]/route.ts:28` throws
   `tile manifest must be an array`, but `data/generated/tile-manifest.json`
   is a flat object. Every tile request returns 500 `DATASET_INVALID` or 503.
   Reproduced identically on the untouched baseline server on port 3100, so
   this is pre-existing, not a T15 regression. The manifest route works
   because `src/lib/data/manifestSlim.ts` handles the object form. The tile
   route needs the same handling.
2. Only 353 of 9591 tile JSON files exist (`data/generated/tiles`: 353 of
   7941 LOD0, 0 of 1254 LOD1, 0 of 396 LOD2), so the fallback cannot be
   exercised end to end until the pipeline regenerates them.
3. `data/generated/render/boundary.mmt` exists, but no per-tile `.mmt` does
   yet, so the per-tile render path is exercised only by the unit test.
4. The `boundary.mmt` index buffer pairs sequential vertices, so rendering
   it as `lineSegments` produces stray chords across the outline. The
   boundary layer needs segment-pair indices (0,1,2,2,3,4,...) from
   `buildRenderTile.ts` (wave2-4), or the boundary layer needs to be read as
   a `Line`. My geometry path is faithful to the format as written; the
   defect is on the write side.
5. `src/lib/render/loadRenderTile.ts:73` and `src/lib/render/tileWorker.ts`
   do not typecheck against the amended `DecodedRenderTile` (they still
   reference `layer.positions` / `layer.indices` / `layer.ranges` and the
   removed `MainToWorkerMessage`). Those are wave2-5 files; I did not touch
   them.
