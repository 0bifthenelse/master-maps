## 1. Single source of truth

`scripts/data/bdtopoLayers.ts:19-51` declares `BD_TOPO_LAYERS` as a 31-entry `as const satisfies readonly BdtopoLayerSpec[]` tuple. Both the exporter and the normalizer derive from it, so a layer can never be exported without being normalized (W1 gap at `normalizeBdtopo.ts:279-286` and `normalize.ts:867` was two hand-maintained lists that had to be edited in lockstep).

Derived exports:

- `ADOPTED_LAYERS: ReadonlyMap<string, BdtopoLayerSpec>` keyed by output filename, consumed by `normalize.ts:867-869`.
- `ADOPTED_OUTPUT_FILES: readonly string[]`.
- `layerNameForOutput(file)`, the normalizer dispatch key.

### 2.1 `haie` exclusion, and the `zone_de_vegetation` LOD gate

`haie` (413 239 records) stays excluded. `zone_de_vegetation` is adopted but gated, which is the documented requirement (W1_T02 gap 21) and is enforced at export time, in SQL, before any geometry is written:

```
nature IN ('Bois','Forêt fermée de feuillus','Forêt fermée mixte','Forêt fermée de conifères',
           'Forêt ouverte','Lande ligneuse','Peupleraie','Vigne','Verger')
AND ST_Area(geometrie) >= 2000
```

Measured threshold effect on the department (ogrinfo SQL, `zone_de_vegetation`): 130 522 records for the nine natures, of which **48 206 pass at 2000 m²**, 12 320 of those are `Bois`. At 5000 m² only 11 records survive, which is why 2000 is the threshold. Measured export size: **185 275 983 B for 48 206 features**, against 466 944 473 B for the unfiltered 259 207 (a 2.5x reduction, and the unfiltered export is larger than the four original files combined, as W1 predicted).

`Haie` is excluded from the nature list because `zone_de_vegetation.nature = 'Haie'` (127 393) duplicates the excluded `haie` layer.

### 2.2 `zone_d_habitation` and `commune` gates

- `zone_d_habitation`: `importance IN ('5','6')`. W1 section 3.12 measures the full distribution (4: 15 075 · 5: 10 497 · 6: 8 878); only 19 375 polygons are towns worth a fill, versus 36 138 hamlet polygons. Higher-importance settlements overlap the smaller ones at render time, so exporting all of them would triple the landuse payload for no visual gain.
- `commune`: `chef_lieu_d_arrondissement = 1` (15 arrondissements, the W1 value at section 2.4 is 693 in-envelope records of which only the chef-lieux are search-worthy). Admin Express remains the render authority; this is search-only.

Both gates are `-dialect SQLITE -sql "SELECT * FROM <layer> WHERE <filter>"` (`fetch-bdtopo.ts:269-272`). Verified GDAL 3.13.1 accepts a parenthesised subquery in the layer argument with an error (`Couldn't fetch requested layer`), so the SQL-dialect form is the only working one; it is verified working with accented literals and `ST_Area`.

### 3.1 Field parsing now performed

- `importance` → `PlaceFeature.importance` (BD TOPO ships it as a String, so `importanceValue` coerces and range-checks 1-6; `normalizeBdtopo.ts:411-414`).
- `nature` → the per-kind subtype table, matched through an NFD-folded lowercase key (`folded`, `normalizeBdtopo.ts:286-288`).
- `position_par_rapport_au_sol` → `RoadFeature.bridge` / `tunnel` / `stratum`, and recorded in `sourceMetadata`.
- `fictif` → `WaterFeature.fictiveAxis` for lines; `confidence: "medium"` for any layer (`normalizeBdtopo.ts:879`).
- `persistance` → `WaterFeature.intermittent` (`Intermittent` and `Sec` both true).
- `classe_de_largeur` → `WaterFeature.width` in metres, 4 measured classes (`normalizeBdtopo.ts:420-425`), with `widthInferred` set when the class is absent (`Sans objet`, `En attente de mise a jour`).
- `hauteur` → `BuildingFeature.height`, `StructureFeature.height`, `reservoir` height, pylon height. Now non-negative rather than strictly positive, so the 205 zero-height buildings W1 section 3.5 measured are kept (`nonnegative`, `normalizeBdtopo.ts:416-418`).
- `nombre_d_etages` → `BuildingFeature.levels`, including 0.
- `toponyme`, `libelle`, `categorie` → `FeatureBase.name`, `PoiFeature.poiType` (`erp:<categorie>` per contract) and `PoiFeature.category`, `LanduseFeature.sourceMetadata.category`.
- `etat_de_l_objet` → `status: "uncertain"` for `En ruine`, `active` otherwise.

### 3.2 Requirements called out explicitly in the task

- **Fictive water axes and fictive roads stay in canonical data.** Nothing is filtered on `fictif`; `fictiveAxis` and `sourceMetadata.fictif` mark them. The renderer skips them (contract section 1).
- **Rail lines are `kind=transport transportType=rail` with LineString geometry, never point POIs.** Verified on the real export below: 256 of 256 produced features are `transport`/`rail`.
- **`zone_d_habitation` → `kind=place` with `importance`.** `placeType` comes from `nature`: `Lieu-dit habite` → `hamlet`.
- **`toponymie` → `place` points with `placeType` from `classe_de_l_objet`.** The table `PLACE_TYPE_BY_OBJECT_CLASS` (`normalizeBdtopo.ts:397-418`) covers all 20 classes W1 section 3.14 measured.
- **`erp` → `kind=poi`.** `poiType` is `erp:<categorie>`, `name` is `libelle`, `category` is `activite_principale`.

### 3.3 Identity and provenance

`stableId` is `ign-bdtopo:<gpkglayer>/<cleabs>`, unchanged in shape so existing stable ids do not move. The four original layers used the export *name* (`ign-bdtopo:building/...`, and tests pin `ign-bdtopo:building/1` at `tests/unit/conflation.test.ts:31` and `ign-bdtopo:surface/1` at `tests/unit/osm-geometry-precedence.test.ts:45`); those two tests construct synthetic ids, so no data migration is implied, but the id vocabulary is now uniform across all 31 layers. `toponymie` has no `cleabs`, so its identity is `<classe_de_l_objet>/<cleabs_de_l_objet>` (`toponymyIdentity`, `normalizeBdtopo.ts:456-461`), which is deterministic and unique per (object, class) pair.

Every feature carries one `provenance` record (winner `IGN BD TOPO`, priority 100) and one `sourceRef` with `source: "IGN BD TOPO"`, `license: "Licence Ouverte / Open Licence 2.0"`, and the edition in the URL (`https://geoservices.ign.fr/bdtopo (edition 2026-06-15)`), read from `data/intermediate/bdtopo-manifest.json:edition` in `normalize.ts:972-973`. The edition goes in the URL, not the `source` string, because `SourceReferenceSchema` is `.strict()` and `validate.ts:111` matches on `source === "IGN BD TOPO"`.

Search-only layers get `sourceMetadata.adoption = "search"` and `sourceMetadata.sourceLayer`, so a renderer can skip them without a second lookup (`normalizeBdtopo.ts:883-885`).

## 4. Export changes in `fetch-bdtopo.ts`

- The Gers manifest now carries `outputs` (W1 gap 17), each entry with `name`, `layer`, `file`, `adoption`, `filter`, `recordCount`, `sha256`. The Auch manifest uses the same `manifestOutput` shape, so the two are no longer divergent.
- `validateGeoJson` and the `GeoJsonFeature`/`GeoJsonCollection` interfaces are gone. The old validator did `JSON.parse` on the whole export to count features, which meant loading a 507 MB file into a `NODE_OPTIONS=--max-old-space-size=12288` heap. `measureGeoJson` (`fetch-bdtopo.ts:227-240`) streams the file once, counting `"type": "Feature"` occurrences and hashing the same bytes, in constant memory. This is the difference between the pipeline needing 12 GB and not needing it, now that a single layer can be 185 MB and there are 31 of them.
- Empty exports are a hard error naming the layer, the output file and the filter (`fetch-bdtopo.ts:288`), so a mistyped SQL gate fails loudly instead of silently producing a file the normalizer will skip.
